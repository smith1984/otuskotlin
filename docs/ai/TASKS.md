# Типовые задачи и промпты для AI-агента

> Этот файл — дополнение к [`/CLAUDE.md`](../../CLAUDE.md). Здесь собраны
> 4 наиболее частых сценария работы с проектом VAFS, готовые промпты и
> критерии приёмки. Используй их как шаблоны: подставь свои значения и
> запускай.

Для каждого сценария указано:

- **Промпт** — формулировка, которую можно скопировать в чат с агентом.
- **Ожидаемый формат ответа** — что должно прийти в обратном сообщении
  (структура из §3 `CLAUDE.md`).
- **Критерии готовности** — как проверить, что задача закрыта.

## Сценарий 1 — добавить новую валидацию в biz-цепочку

**Когда применять:** появилось новое требование к Rule (например, поле должно
проходить дополнительную проверку: длина, формат, диапазон, разрешённый список
значений).

**Затрагиваемые модули:** `m4-hw6-vafs-biz` (только `validation/`) +
соответствующие тесты в `m4-hw6-vafs-biz/src/test/kotlin/`.

### Промпт

```text
Добавь в модуль m4-hw6-vafs-biz новую validation-handler:

- Имя: <ValidateXxx>.kt — следуй существующему паттерну
  (ValidateIdNotEmpty, ValidateDescriptionHasContent, ...).
- Логика: <человеческое описание проверки>.
- Ошибка: добавь в State.FAILING + сформируй VafsRuleError с
  group="validation", code, message, level=Error.
- Подключи новый handler в цепочку validation внутри VafsRuleProcessor —
  в правильном порядке (после ValidateIdNotEmpty, перед repo-этапом).
- Напиши unit-тест в src/test/kotlin/<тот же относительный путь>:
  - happy path: handler не меняет state
  - sad path: handler выставляет state=FAILING и errors[] не пуст

Соблюдай:
- никаких `!!`,
- именование handler'а — глагол + существительное,
- DSL `lib-cor` (не вручную обходить чейн).

Команда проверки: ./gradlew :m4-hw6-vafs-biz:test
```

### Ожидаемый формат ответа

1. **План** — 3–5 шагов (создать handler, подключить в processor, написать
   2 теста, прогнать).
2. **Изменения** — `Write` нового файла handler'а + `Edit` в
   `VafsRuleProcessor.kt` + `Write` теста.
3. **Пояснение** — почему handler ставится в этой позиции цепочки.
4. **Шаги проверки** — `./gradlew :m4-hw6-vafs-biz:test --tests "*ValidateXxx*"`,
   ожидаемый вывод «BUILD SUCCESSFUL» с зелёными тестами.

### Критерии готовности

- Файл `ValidateXxx.kt` существует, следует именованию (`<Глагол><Существительное>.kt`).
- В `VafsRuleProcessor.kt` handler подключён в `chain` с явным `title = "..."`.
- В тестовом файле — минимум **happy path** и **sad path**.
- `./gradlew :m4-hw6-vafs-biz:test` зелёный.
- В трейлерах коммита есть `AI-Tool: ...` (см. §4 `CLAUDE.md`).

## Сценарий 2 — расширить контракт repo новым методом

**Когда применять:** API нужен новый способ выборки правил (например,
`findByPriorityRange(min, max)` или `findActiveOnly()`). Это
**multi-module задача**, потому что репозиторий имеет 4 имплементации.

**Затрагиваемые модули:**

- `m5-hw7-vafs-repo-stubs` — обновить интерфейс `IRuleRepository` +
  обновить stub-реализацию.
- `m5-hw7-vafs-repo-in-memory` — добавить логику поверх cache4k.
- `m5-hw7-vafs-repo-postgresql` — добавить запрос через Exposed; если нужна
  новая колонка/индекс — Liquibase changeset в
  `infra/volumes/postgres/liquidbase/changelog.yaml`.
- `m5-hw7-vafs-repo-tests` — добавить контрактный тест в общем модуле.
- `m4-hw6-vafs-biz` — если бизнес-логика должна вызывать новый метод —
  обновить соответствующий handler в `repo/`.

### Промпт

```text
Добавь в IRuleRepository метод <signature>:
suspend fun <name>(<params>): <return>

Реализуй во всех имплементациях:
1. m5-hw7-vafs-repo-stubs — стабовая реализация (вернуть фиксированный
   список из VafsRuleStub.NUMBER_LIST или эквивалент).
2. m5-hw7-vafs-repo-in-memory — фильтрация уже хранящихся в cache4k
   записей.
3. m5-hw7-vafs-repo-postgresql — Exposed-запрос; если нужно
   новое поле/индекс — добавь Liquibase-changeset с явным "id":
   "<ddmmYY>-<short-description>".

Добавь в m5-hw7-vafs-repo-tests общий тест-кейс DbXxxTest, чтобы все
имплементации проверялись одинаково.

Соблюдай: suspend-стиль, никаких блокирующих вызовов в repo.

Команды проверки:
- ./gradlew :m5-hw7-vafs-repo-in-memory:test
- ./gradlew :m5-hw7-vafs-repo-postgresql:test
```

### Ожидаемый формат ответа

1. **План** — 5–7 шагов с явным списком модулей в порядке зависимости (stubs
   → in-memory → postgresql → tests → biz).
2. **Изменения** — серия `Edit` для интерфейса и каждой реализации; новый
   контрактный тест в repo-tests.
3. **Пояснение** — почему именно эта сигнатура (типы параметров, suspend,
   `Result<>` или throws), какая стратегия запроса в Exposed.
4. **Шаги проверки** — последовательные `./gradlew` команды для каждого
   repo-модуля.

### Критерии готовности

- Интерфейс `IRuleRepository` обновлён, все 3 имплементации компилируются.
- Контрактный тест есть в `m5-hw7-vafs-repo-tests` и **наследуется** в каждом
  имплементационном модуле — не дублирован.
- Если был изменена БД-схема — Liquibase-changeset идемпотентный
  (`runOnChange: false`) и обратный (rollback) корректен.
- Все 3 модуля repo проходят тесты.

## Сценарий 3 — покрыть существующий модуль/handler тестами

**Когда применять:** для существующего файла нет тестов или их мало.
Цель — увеличить coverage без изменения поведения.

**Затрагиваемые модули:** только тестовая часть `<module>/src/test/kotlin/`.

### Промпт

```text
В модуле <module-name> для класса/файла <Path/To/File.kt>:

1. Прочитай реализацию.
2. Перечисли все ветви исполнения и edge cases (минимум: happy path,
   null/empty input, ошибочные значения, корректные граничные значения).
3. Для каждой ветви напиши отдельный тест-метод в стиле существующего
   набора тестов модуля (kotlin-test-junit + runTest для suspend).
4. Не меняй production-код. Если нашёл реальный баг — зафиксируй
   findings в отдельном комментарии под планом, но не исправляй
   без отдельной задачи.

Команда проверки: ./gradlew :<module>:test
```

### Ожидаемый формат ответа

1. **План** — таблица «ветка / тест-имя / ожидание».
2. **Изменения** — 1 файл с тестами (или серия по одному на ветку, если
   политика модуля такая).
3. **Пояснение** — почему именно такие ветви выбраны, какие edge cases
   реалистичны (а какие — defensive over-test).
4. **Шаги проверки** — `./gradlew :<module>:test`, и желательно
   `--tests "*<NewTestPattern>*"` для прицельного прогона.

### Критерии готовности

- Каждая ветка `if/when/?:` в production-коде имеет хотя бы один тест.
- Тесты не зависят друг от друга (`@BeforeEach` для setup, `runTest` для
  suspend-кода).
- `./gradlew :<module>:test` зелёный, **число тестов выросло** относительно
  baseline.

## Сценарий 4 — рефакторинг без изменения поведения

**Когда применять:** код стал нечитабельным, дублируется, использует
устаревший API; нужно почистить, **не меняя observable behavior**.

**Затрагиваемые модули:** один модуль (если изменение локальное) или
несколько (если дубликат вынесен в `m2-hw3-vafs-common` или `lib-cor`).

### Промпт

```text
Сделай рефакторинг файла/класса <File.kt>:

Цель: <конкретная — например "вынести повторяющуюся логику X в helper
в m2-hw3-vafs-common", или "заменить deprecated API Y на Z", или
"разбить функцию foo() длиной 80 строк на 3 чистых функции">.

Ограничения:
- ни одно публичное API не меняется (не трогай сигнатуры функций,
  экспортируемых из модуля);
- ни один существующий тест не должен потребовать правки. Если
  потребовался — это нарушение цели; стоп.
- если изменения переходят границу модуля, в плане явно укажи новый
  модуль и проверь зависимости в build.gradle.kts.

После: прогон всех тестов модуля и явное сравнение поведения через
один-два sanity-теста.

Команды:
- ./gradlew :<module>:test
- если модуль biz — также ./gradlew :m4-hw6-vafs-biz:test
```

### Ожидаемый формат ответа

1. **План** — 3–5 шагов (вынести в X, заменить вызовы, прогнать тесты).
2. **Изменения** — последовательность `Edit` без затрагивания тестов.
3. **Пояснение** — какая идиома Kotlin/SOLID-принцип за изменением;
   обязательно — почему **существующие тесты** доказывают сохранение
   поведения.
4. **Шаги проверки** — все тесты затронутых модулей зелёные.

### Критерии готовности

- Ни один файл `*Test.kt` не отредактирован (исключение — если задача
  явно «отрефакторь имена в тестах»).
- Diff сосредоточен в одном модуле (или явно объяснено, почему нужно
  больше).
- `./gradlew build` зелёный.
- Линтер (если включён) не показывает регрессии.

## Антипаттерны (что **не** делать)

| Антипаттерн | Почему плохо |
|---|---|
| Добавлять `!!` в production-код | проект явно избегает этого; вместо этого `?:`, `requireNotNull(...)`, `.also { check(it != null) }` |
| Менять имена модулей `m{N}-hw{M}-vafs-*` | ломает внешние ссылки и историю курса |
| Писать в `m2-hw3-vafs-api-v1-jakson/build/generated/...` руками | папка пересоздаётся `openApiGenerate`; меняй `specs/*.yaml` |
| Использовать `runBlocking` в тестах | `runTest` корректно работает с TestCoroutineScheduler; `runBlocking` блокирует поток и даёт фейковые таймауты |
| Дублировать тесты репо в каждом репо-модуле | контракт уже в `m5-hw7-vafs-repo-tests`; наследуйся, не копируй |
| Один большой коммит на 5 модулей | разбивай по логическим единицам; AI-Tool trailer — на каждый |
| Менять `gradle.properties` без задачи на обновление стека | стек закреплён, мажорные апгрейды требуют отдельной верификации |

## Шаблон git-коммита для AI-агента

```
<scope>: <короткое описание (≤72 символов)>

<тело сообщения, при необходимости — что и почему>

AI-Tool: <Имя инструмента> (<модель/версия>)
Refs: <docs/ai/TASKS.md#scenario-N (опционально)>
```

Пример:

```
biz: add ValidatePriorityWithinRange handler

Validates that Rule.priority is in [0..1000] range. Plugged in
the validation chain right after ValidatePriorityNotEqualZero.

AI-Tool: Claude Code (Opus 4.7, 1M ctx)
Refs: docs/ai/TASKS.md#1
```
